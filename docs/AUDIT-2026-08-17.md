# DocAgent — Audit, 2026-08-17

Read-only investigation of the repository and the live Railway production
deployment. No application code was modified.

**Scope of evidence.** Everything below is either (a) read directly out of the
code at a cited `file:line`, (b) observed from the live deployment via Railway
read APIs / HTTP requests, or (c) produced by running the pipeline locally
against the two committed fixture PDFs. Where I could not establish something,
it is stated as unverified rather than asserted. Section 9 lists what remains
open.

**Secrets.** No secret values appear in this report. Secrets are referred to by
variable name only. One exception is called out as a finding (P1) because the
credential is already public.

## 0. Executive summary

The product is a working single-tenant AI extraction tool with a genuinely
capable template-driven extraction engine, deployed as two Railway services off
one repo. Both fixture documents extracted **correct values** on the paths that
matter. That is the good news, and it is real.

The problems are not in the extraction math. They are in four places:

1. **The repository is public and contains a real customer invoice** with a
   named individual, street address, two phone numbers and a partial card
   number, plus a live-format Groq API key. This is the only finding that
   can cost you a client before you ever demo.
2. **Config is declared in one vocabulary and read in another.** `CORS_ORIGINS`
   and `MAX_FILE_SIZE_MB` are set in production; the code reads
   `ALLOWED_ORIGINS` and `MAX_UPLOAD_SIZE_MB`. CORS is additionally hardcoded.
   Nine declared settings are never read at all. This is the direct mechanism
   behind failure pattern 1.
3. **The extraction pipeline is conditioned on a nondeterministic LLM
   segmentation step, and the accuracy fixes are tuned against one instance of
   its output.** I reproduced a live [ACCURACY] regression on the committed
   balance-sheet fixture: the deployed code writes a fabricated duplicate line
   item that the June captured output does not contain. The mechanism is fully
   traced in §6.4. This is failure pattern 2, and it is also failure pattern 1
   — the fix that causes it (S5) was added in the currently-deployed commit to
   fix a different bug.
4. **There is no automated verification of extracted values anywhere in the
   repo.** Zero assertions. Zero expected-value comparisons. `npm run lint` has
   never been configured and prompts interactively. 26 changes to the core
   extraction path across two commits were verified by `py_compile`, `tsc`, and
   a human reading a spreadsheet.

The single highest-leverage structural fact: **the routing decision that picks
which of three extraction engines runs is made by matching the user's column
header text against a hardcoded list of 16 English words**
(`extract.py:1416`). A client whose balance-sheet value column is headed
`2024`, `USD`, `Q4`, `Actual` or blank silently gets routed to the wrong engine
and gets a mostly-blank spreadsheet, with no error anywhere.

### 2.3 Layer 1 / Layer 2 / Layer 3 (the structural path, path C)

- **Layer 1** `_understand_document` (`extractor.py:~143`): one Gemini vision

  template-derived single-doc map on failure.
- **Layer 2** `_run_all_extractions` → `_extract_section` (`:334`): one narrow

## 3. Config versus code

### 3.1 The CORS defect — confirmed, and worse than described

`app/main.py:226-232`:

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],          # hardcoded
    allow_credentials=False,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

`settings.ALLOWED_ORIGINS` (`config.py:74`) is **read nowhere in the
codebase** — `grep -rn "settings.ALLOWED_ORIGINS"` returns zero hits.

Live confirmation:

```
$ curl -i https://docagent-univer-production.up.railway.app/health \
       -H 'Origin: https://evil.example.com'
access-control-allow-origin: *

$ curl -i -X OPTIONS .../api/auth/login -H 'Origin: https://evil.example.com' \
       -H 'Access-Control-Request-Method: POST'
access-control-allow-methods: DELETE, GET, HEAD, OPTIONS, PATCH, POST, PUT
access-control-allow-origin: *
```

No `access-control-allow-credentials`. Exactly as you described.

**There are two independent defects stacked here**, and this is the thing to
internalise because it is the template for the whole section:

1. The middleware ignores the Settings field.
2. **The production env var is named `CORS_ORIGINS`. The Settings field is
   named `ALLOWED_ORIGINS`.** Pydantic's `extra="ignore"` (`config.py:18`)
   swallows the mismatch silently. So even if you fix the middleware to read
   `settings.ALLOWED_ORIGINS`, `CORS_ORIGINS` would still be ignored, the
   default `["*"]` would apply, and the observable behaviour would not change
   — you would "fix" it and see nothing happen.

Mitigating detail worth stating plainly, because it changes the priority: the
frontend authenticates with a **Bearer token from `localStorage`**
(`lib/api.ts:9-11`), not a cookie. So `allow_origins=["*"]` with
`allow_credentials=False` does not enable drive-by authenticated requests the
way a cookie session would. The exposure is that the API is open to
unauthenticated cross-origin scripting from any page, and any leaked token
works from anywhere for 24 hours (§4.7). Real, but not a session-riding hole.

### 3.4 Why this section is the answer to failure pattern 1

Six of your production env vars are inert, and **not one of them produces an
error, a warning, or a log line**. `pydantic-settings` `extra="ignore"` makes a
misspelled or renamed variable indistinguishable from an unset one. So the
config surface *looks* like it has 15 knobs and actually has 9.

That is the mechanism: when you change a setting and the behaviour does not
change, the natural next move is to change code instead — and now you have a
hardcoded value shadowing a declared setting, which is exactly how
`main.py:228` came to exist. Every one of those hardcodings is a place where a
future correct fix will appear to do nothing, and where two people reading the
same repo will disagree about what production is doing.

exception, and the exception is backwards.** The hardest problem in the product
(structural balance-sheet segmentation and per-section extraction, path C) runs
entirely on the weakest tier. The easiest problem (a labeled invoice with a
known cell map, path D) is pinned to the stronger tier. Template understanding
— a single cached decision that determines which engine every future document
of that template uses — also runs on Flash-Lite.

Confirmed in my own runs: `[GEMINI] vision:gemini-2.5-flash-lite` on all five
calls of the structural balance-sheet run; `[GEMINI] vision:gemini-2.5-flash`
when I left `GEMINI_MODEL` at the code default.

**Silent fallback to another model.** Yes, two mechanisms:

1. `gemini_client.py:162` / `:215` build `ordered = [model, self._good_model, self._preferred] + CANDIDATES` and try each until one returns 200. `CANDIDATES` (`:78-83`) is `[gemini-2.5-flash-lite, gemini-2.5-flash, gemini-flash-latest, gemini-flash-lite-latest]`. So a transient non-auth HTTP error on flash-lite **silently promotes the call to `gemini-2.5-flash`** and caches it in `self._good_model` (`:171`, `:224`) for the rest of that job. No log distinguishes "ran on the configured model" from "fell through to a different one" beyond the `[GEMINI] vision:<model>` line.
2. `_make_response` (`:243-260`) on a JSON parse failure retries via `self._call(...)` — **without the `model=` override and without the images**. A vision call that fails to parse is retried as a text-only call against `raw[:1000]`. For the CBM path this silently drops from flash to whatever `_good_model` holds, and drops the document.

**Silent fallback to another provider.** `LLMRouter.extract` (`:138-166`) tries
`primary` then `fallback`. With `PRIMARY_LLM=gemini`, `fallback` is
`self._groq`, which exists because `GROQ_API_KEY` is set. **The Groq fallback is
completely dead.** I queried `GET https://api.groq.com/openai/v1/models` with

All three configured Groq models are decommissioned, and the account is offered

- When Gemini fails, the fallback also fails, and `LLMRouter.extract` returns

- **`PRIMARY_LLM=groq` — the code default (`config.py:40`) — is a completely

### 4.4 No Redis, no Celery — does extraction run inside the HTTP request?

**No.** `POST /api/extract/upload` spawns `threading.Thread(target=_run_extraction_sync, …, daemon=True)`
at `extract.py:236-243` and returns **202** at `:245`. Railway's request
timeout does not apply to the extraction work at all.

**What a 20-file batch actually does:**

- **The upload request itself** is subject to the request timeout — it must
  transfer up to 20 × 50 MB = 1 GB and, worse, **reads every file twice**:
  once at `extract.py:182` to validate size, then `await f.seek(0)`, then again
  at `:232` to save. Starlette spools `UploadFile` above ~1 MB to a temp file,
  so peak memory stays bounded, but the wall-clock transfer time for a large
  batch is real and is the one place a timeout can bite.
- **The extraction** then runs unattended: per file, `RATE_LIMIT_DELAY` = 2.0 s
  between documents (`:6336-6339`) plus the LLM calls. On the structural path I
  measured **5 Gemini calls for a 1-page, 2-section balance sheet** (1 × L1 +
  4 × L2). A realistic 4-section balance sheet is ~5 calls at 3–8 s each, so
  ~20–40 s per document; 20 files ≈ 7–15 minutes in a daemon thread.

The real failure modes are not timeouts:

1. **`daemon=True` + no recovery.** On redeploy, restart, or crash the thread
   is killed without running its `finally`. The job row stays
   `status="processing"` **forever** — nothing scans for orphaned jobs at
   startup. The UI polls it at 2 s intervals indefinitely. Given autodeploy on
   push (§1.2), any push during a long batch strands that job.
2. **Unbounded concurrency.** Nothing limits how many extraction threads exist.
   Each one builds its own `sa_engine(db_url)` at `extract.py:6157` **without
   the app's pool settings** (`models.py:267` configures `pool_size=10,
   max_overflow=20`; the thread's engine gets SQLAlchemy defaults, `pool_size=5,
   max_overflow=10`). N concurrent jobs = N independent connection pools
   against one Postgres.
3. **Cancel does not cancel.** `DELETE /api/jobs/{id}` sets
   `status="cancelled"` (`:8078`) but there is no cancellation check anywhere
   in the loop, and `:6342` unconditionally sets `status="completed"` at the
   end. Cancel is a temporary relabel that the thread overwrites.

### 4.7 `ACCESS_TOKEN_EXPIRE_MINUTES=1440` — refresh and revocation

**No refresh mechanism.** No refresh endpoint, no refresh token, no rotation.
`grep -rn "refresh"` over `backend/app` returns nothing token-related. The
frontend stores `da_token` + `da_token_exp` in `localStorage`
(`lib/api.ts:13-17`) and redirects to `/login` on 401. A user is logged out
hard at 24 hours.

**Revocation — one mechanism, and it works.** `get_current_user`
(`core/auth.py:82`) re-queries the DB on **every request** with
`User.is_active == True`. So `DELETE /api/admin/users/{id}` or setting
`is_active=False` **does** invalidate that user's tokens immediately. That is a
genuine, working kill switch, and it is the only one.

**What is not revocable:**

- **A password change does not invalidate existing tokens.**
  `update_user` (`admin.py:81-84`) rewrites `password_hash` and nothing else.
  There is no `jti`, no denylist, no `password_changed_at` compared against the
  token's `iat` — the JWT carries `iat` (`core/auth.py:48`) but nothing ever
  reads it. A stolen token survives the password reset for its full 24 hours.
- No `iss`/`aud` claims; nothing binds a token to a session, device, or IP.

Combined with §3.1 (`allow_origins: *`), a leaked token is usable from any
origin for 24 hours and the only way to stop it is to deactivate the account.

#### The mechanism, in full

It runs through five components, each of which does exactly what it was
written to do.

**1. Layer 1's answer changed.** The committed artifact's own
`raw_llm_responses` records the June Layer-1 document map:

```json
"sections": [ {"heading": "Current Assets",      "item_count": 5, ...},
              {"heading": "Current Liabilities", "item_count": 5, ...} ]
```

Two sections, `item_count: 5` each (4 line items + the total row counted as an
item of the section). Today, on the identical PDF and the **identical prompt**
— I diffed `_understand_document`'s prompt text between `eb7ef34` (2026-06-27,
the commit era of the capture) and `cad3329` and it is unchanged except for the
`_L1_MAX_PAGES` cap — Layer 1 returns **four** sections:

```
[L1] document map: 1 documents, 4 total sections
  Current Assets  |  Current Liabilities  |  Total Current Assets  |  Total Current Liabilities
```

The two "Total …" entries are not sections; they are the totals row, promoted
to sections with `item_count: 1`.

**2. Layer 2 extracts the phantom sections.** Asked to extract "Total Current
Assets", the model returns the whole assets column — 5 rows.

**3. S5 truncation keeps the wrong row.** `extractor.py:365-369`:

```python
expected = int(section_info.get("item_count", 0) or 0)
if expected > 0 and len(out_rows) > expected * 1.5:
    out_rows = out_rows[:expected]        # keeps the FIRST `expected` rows
```

5 > 1 × 1.5, so it truncates to `out_rows[:1]` — and the first row of the
assets column is **"Cash & Cash Equivalents 168,000"**, not the total. Log:

```
[L2] section 'Total Current Assets' truncated 5 -> 1 rows (item_count=1;
     excess likely belongs to the next section)
```

**4. Section matching routes the phantom into the real group.**
`_match_group` (`extract.py:6787-6810`) stage 2 is a substring test:
`_nrm("Current Assets")` = `"currentassets"` is a substring of
`_nrm("Total Current Assets")` = `"totalcurrentassets"` → match. The phantom's
single row is `extend`ed onto the real group's 4 rows (`:6842`) → 5 rows →
written at rows 2–6. Stage 3 cannot save it either: `_SEM_STOP`
(`:6713`) **deliberately strips the token `"total"`**, making a section and its
own total semantically identical by design.

**5. Both dedup guards miss it, and this is where the two failure patterns
meet.**

- Content-signature dedup (`:6766-6781`) requires **identical** row content.
  1 row ≠ 4 rows → no match.
- Superset dedup (`:6829-6832`) requires `len(r1) > len(r2)` — it only drops
  **supersets**. The truncated phantom is a **subset** (1 row vs 4).

**Before S5 existed, the superset guard caught this.** Untruncated, "Total
Current Assets" would have had 5 rows — a genuine superset of the 4-row real
section — and every condition at `:6829-6832` would have held
(`4/4 ≥ 0.9` ✓, `5 > 4` ✓, `_match_group("Current Assets")` ✓,
`len(l1 - l2) == 1 ≤ 1` ✓), dropping it. **S5 converted a superset the writer
knew how to discard into a subset it does not, by truncating it.**

Layer 3 does catch the result and flags it:

```
[L3] needs_review: Section 'Total Current Assets' total mismatch —
     items sum to 168000, own total B10 shows 415000
```

`needs_review = True`. So the document lands in the review queue rather than
being silently wrong — a real save. But **the exported spreadsheet still
contains a fabricated line item**, and if a client opens the download before
reading the flag, they see an invented row in their balance sheet.

**This is your two failure patterns in one defect.** Pattern 2: every function
is individually correct — S5 truncates as specified, `_match_group` matches as
specified, the dedup guards guard exactly what they were tightened to guard —
and the output is wrong. Pattern 1: S5 was added in the **currently-deployed
commit** to fix section bleed, and it broke a dedup guard that had been
deliberately tightened two commits earlier (`7718473`) to stop over-dropping.
The two fixes are in direct tension and nothing in the repo holds both.

**And the trigger is not in your code.** The Layer-1 prompt did not change; its
answer did. Cause not established: either provider-side drift in
`gemini-2.5-flash-lite`, or the June capture ran on a different
`GEMINI_MODEL` — the artifact does not record which model made the Layer-1 call,
so **I cannot distinguish these**. Either way the structural conclusion holds:
**the entire structural pipeline is conditioned on a nondeterministic LLM
segmentation step, and every accuracy fix downstream is tuned against one
observed instance of its output.** That is the root mechanism, and it is
architectural, not a bug.

#### The ones most likely overfit

Ranked by how much damage a wrong value does, and how likely it is wrong for a
client who is not you.

**1. `_VALUE_KW` (#1) — the worst, by a distance.** This 16-word list decides
whether `column_groups` is non-empty, which decides `template_type` (#2), which
decides **which of three extraction engines runs**. A structural template whose
amount column is headed `2024`, `FY24`, `Q4`, `USD`, `GBP`, `Actual`,

`template_type` is not `structural` → the balance sheet is routed to the

column."** The structural path was authored and verified against templates that
say "Amount", including both committed fixtures. This is my single best
candidate for "the code looks correct but the extracted values are wrong" on a
new client's first template.

**2. S5's `* 1.5` and `rows[:expected]` (#5).** Demonstrated wrong above. The
ratio is defensible; **the slice is the bug** — it assumes over-extraction
appends the *next* section's rows at the end, so keeping the first N is safe.
When the "section" is a totals row, the first N is the neighbouring section's
first line item. Authored against exactly one observed case.

header containing "Net" or "Balance" is disqualified from being a section
header. A template with **"Net Assets"**, **"Net Position"**, **"Balance
Sheet"** or **"Balances"** as a section title collapses its section boundaries.
"Net Assets" is standard in not-for-profit and fund accounting; "Net Position"
is standard in government (GASB) reporting. Two of the eight strings are
ordinary English words that appear in legitimate section names.

**4. The A1 threshold cluster (#11–#13) against the dedup cluster (#14–#16).**
Six numbers tuned against three specific production jobs (145, 149-151),
pulling in opposite directions: A1 loosens matching so "Long-term Liabilities"
finds "Non current liabilities"; the dedup tightening stops over-dropping.
`_SEM_STOP` stripping `"total"` is what makes a section indistinguishable from
its own total — required for A1, and the direct enabler of the §6.4 defect.
There is no input on which both behaviours are asserted.

**5. `maxOutputTokens: 8192` with no `finishReason` check (#25).** A long
bank statement or multi-page line-item table will exceed 8192 output tokens.
`_post` (`gemini_client.py:112-119`) reads `candidates[0].content.parts[0].text`
and **never inspects `finishReason`**. Truncated JSON usually fails
`_parse_json_robust` and surfaces as an error — but `_parse_json_robust`'s
`text.find('{') / text.rfind('}')` span extraction (`:47-51`) will succeed
whenever truncation happens to land at a balanced brace, returning a **partial
object reported as success**. Silent row loss on exactly the documents a client
would use to judge the product.

**6. `_L1_MAX_PAGES = 20` (#8) compounded by `preprocessor`'s own 20-page image
cap (#29).** Two independent 20-page caps. A 40-page bank statement: pages
21-40 are never rendered to images at all, so Layer 1 cannot see them **and
neither can Layer 2** (which "always sends each section's own page" — a page
that does not exist in `page_images`). The result is a partial extraction that
reports success. Nothing warns that pages were dropped.

**7. Cost rates (#32) plus the token undercount (D6).** Three wrong rates and a
~5x token undercount, feeding a page you would use to price the product.

### P7 · [PRODUCTION] The extraction thread is unrecoverable, unbounded, and uncancellable

`extract.py:236-243` · `:6155-6160` · `:6342` · `:8073-8079`

Three distinct defects in one mechanism.

**Orphaned jobs.** `threading.Thread(..., daemon=True)` is killed on process
exit without running `finally`. Nothing scans for stale `processing` jobs at
startup. A job interrupted by a redeploy, restart or crash stays
`status="processing"` **forever**, and the UI polls it at 2 s intervals
indefinitely. Since autodeploy fires on every push to `main` (§1.2), any push
during a batch strands that job. A 20-file batch runs ~7-15 minutes
(measured: 5 Gemini calls per structural document, 2 s inter-document delay).

**Unbounded concurrency with a second connection pool.** Nothing limits
concurrent extraction threads. Each builds its own `sa_engine(db_url)` at
`:6157` **without** the app's pool configuration — `models.py:267` sets
`pool_size=10, max_overflow=20`; the thread's engine gets SQLAlchemy defaults
(`pool_size=5, max_overflow=10`). N jobs = N independent pools against one
Postgres.

**Cancel does not cancel.** `DELETE /api/jobs/{id}` sets `status="cancelled"`
(`:8078`), there is no cancellation check anywhere in the loop, and `:6342`
unconditionally sets `status="completed"` at the end. Cancel is a relabel the
thread overwrites, while the LLM spend continues.

To be clear on the question you asked: **extraction is not synchronous in the
HTTP request** — 202 returns immediately and Railway's request timeout does not
apply to the extraction. The upload *transfer* (up to 1 GB for 20 × 50 MB, with
each file read twice at `:182` and `:232`) is the only timeout-exposed part.

### P9 · [PRODUCTION] Passwords are single-round SHA-256, and a password change cannot revoke a token

`core/auth.py:24-37` · `:42-49` · `admin.py:81-84`

`hash_password` is `sha256(salt + password)` — **one round**. The 16-byte salt
defeats rainbow tables but not brute force: single-round SHA-256 is
GPU-crackable at roughly 10^10 guesses/second, so the entire `users` table is
recoverable from a DB dump at a rate limited only by password quality. There is
no bcrypt, scrypt, argon2 or PBKDF2 anywhere. `verify_password` (`:35`) also
compares with `==` rather than `hmac.compare_digest` (timing side channel; low
practical risk over HTTP, but free to fix).

`ACCESS_TOKEN_EXPIRE_MINUTES=1440` with **no refresh and no denylist**. The one
revocation mechanism that works is `is_active` — `get_current_user` re-checks
`User.is_active == True` on every request (`:82`), so deactivating a user kills
their tokens immediately. **A password change does not**: `update_user`
(`admin.py:81-84`) rewrites only `password_hash`; the JWT carries `iat`
(`core/auth.py:48`) but nothing ever reads it, and there is no
`password_changed_at`. A stolen token survives the password reset for its full
24 hours, usable from any origin (§3.1).

### D4 · [PRODUCTION] A bare `except` silently swaps extraction engines mid-request

`extract.py:4266-4274`

```python
if getattr(settings, "USE_NEW_EXTRACTOR", False):
    try:
        return _v3_run(orchestrator, file_path, template_data, ...)
    except Exception as _v3_err:
```

**Mechanism.** **Any** exception in the v4 engine — including a bug introduced

breaks": you fix the v4 engine, an unrelated edge case throws, and the user
gets legacy output that looks plausible and is shaped differently — with the
only evidence in container stdout. Compounding it, the flag suggests two
isolated implementations, but `engine/extractor.py` lazily imports ~15 heavy
primitives back out of `extract.py` (`compute_binding_map`,
`_build_vision_prompt`, `_process_vision_result`, …), so editing the "legacy"

### D6 · [PRODUCTION] Token counts are undercounted ~5x, and three different wrong cost rates are in use

`extractor.py:646-659` · `extract.py:6298,6305-6309` · `gemini_client.py:63` · `analytics/page.tsx:10`

**Mechanism.** `_assemble_result` collects every response's `raw_text` into
`raw_llm_responses`, then sets
`last = next((x for x in reversed(responses) if x is not None), None)` and
`r.extraction_response = last` (`:651-659`). `_run_extraction_sync` then reads
`result.extraction_response.tokens_used` (`extract.py:6298`, `:6305`) — **the
last call only**. My measured structural run made 5 calls totalling
**8,568 tokens**; roughly 1,800 would have been recorded. That is a **~5x
undercount** on the structural path, growing with section count.

On top of that undercount, three independent and all-wrong cost models:

| Location | Rate | Reality |
|---|---|---|
| `gemini_client.py:63` | `$0.075/1M` in + `$0.30/1M` out | Gemini **1.5** Flash rates |
| `extract.py:6308` | `(tokens/1e6) * 0.15` flat, no in/out split | writes `extraction_jobs.total_cost` |
| `analytics/page.tsx:10` | `COST_PER_1K_TOKENS = 0.00015` | `$0.15/1M` blended |

None matches `gemini-2.5-flash-lite`, and none accounts for the CBM path
running on `gemini-2.5-flash` (a materially more expensive tier). Anyone
pricing this product from the analytics page will underprice it substantially.

### D7 · [ACCURACY] The debug harness's provenance column is systematically wrong
