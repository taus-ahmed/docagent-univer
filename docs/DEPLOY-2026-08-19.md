## 1. What changes between `2584bb6` and this branch

### 1.1 Database schema

| change | backward compatible? |
|---|---|
| `column_templates.cell_binding_map` **DROPPED** | **No** — but recoverable, see §2 |
| `column_templates.shape_json` **DROP IF EXISTS** | **Yes — no-op.** Verified: this column does **not exist** in production. It was added and removed within this branch and never shipped. |
| No other table, column, index or constraint changes | — |

Nothing is added. Nothing is renamed. No data is migrated.

The single production row holding a `cell_binding_map` is template **id 24
(`Invoice-Template-101`)**. Its content — 20 extract cells, one `line_items`
table at rows 14–18, 28 static cells, 5 section names — is wholly derivable from
that template's grid, which is unchanged. Nothing in it is unrecoverable.

### 1.2 The boot migration

`_run_migrations()` in `app/main.py` gains two statements:

```sql
ALTER TABLE column_templates DROP COLUMN IF EXISTS cell_binding_map;
ALTER TABLE column_templates DROP COLUMN IF EXISTS shape_json;
```

and loses the `ADD COLUMN IF NOT EXISTS cell_binding_map` line plus the FIX-7
boot cleanup that read it.

**Each statement is individually wrapped in `try/except` with a rollback, so a
failed ALTER logs at DEBUG and boot continues.** A permissions problem cannot
prevent the service starting. `DROP COLUMN` on PostgreSQL is a metadata-only
operation taking a brief `ACCESS EXCLUSIVE` lock; on a table of 19 rows it is
instant.

### 1.3 API contract

| change | backward compatible? |
|---|---|
| `GET /api/jobs/{id}/inferred-templates` **added** (auth-gated, `get_current_user` + `_get_job_or_404`) | **Yes** — purely additive |
| `TemplateResponse.shape` **added**, `Optional[dict] = None` | **Yes** — additive; older clients ignore unknown fields |
| Every other route on `extract.py` and `templates.py` | **Unchanged** — verified by diffing the route decorator sets; no route removed, no path or method altered |

No request schema changed. No response field was removed or retyped.

### 1.4 Config

`USE_NEW_EXTRACTOR` is removed from `Settings`. The variable is **still set on
the Railway service**, which is harmless: `config.py` uses
`extra="ignore"`, so an unrecognised environment variable is silently
discarded and cannot raise at startup. You may delete the variable at your
leisure; it is now inert. (It was already effectively inert — there is one
pipeline.)

### 1.5 Frontend

Four files: `DocAgentSpreadsheet.tsx`, `TemplateEditor.tsx`,
`TemplatePreview.tsx`, `lib/api.ts` (+115 / −78).

| change | backward compatible? |
|---|---|
| The saved grid no longer contains `extractTargets`, and cells no longer carry `extractTarget` | **Only with the new backend.** See §3 — this dictates the order |
| Empty cells inside the used region render as slots automatically | Yes, cosmetic |
| "Extract here" toolbar button removed; status bar counts slots | Yes, cosmetic |
| `ColumnTemplate.shape` / `TemplateShape` types added to `api.ts` | Yes, additive |
| A read-only "Structure:" bar appears when the server supplies a shape | Yes, degrades to hidden |

**Existing templates keep loading.** Old grids still carry `extractTargets` and
per-cell `extractTarget`; the new editor ignores both and derives slots from
emptiness, which produces the same result. They are only stripped if the user
re-saves that template.

### 1.6 Behavioural changes that are not schema or contract

- One extraction pipeline. The legacy inline pipeline, the layout/field/CBM
  paths and the three-layer no-template engine are deleted (~3,250 lines). The
  bare `except` that silently swapped engines mid-request is gone: a failure is
  now a failure and is visible.
- No-template extraction infers a template and runs the same slot pipeline,
  instead of the orchestrator's YAML-schema path.
- Template save no longer makes a Gemini call (`_understand_template` deleted).
  **Saving a template becomes fast and cannot hang** — previously it could block
  an HTTP request for up to ~300s.
- Confidence is tightened (a cell carrying two data is no longer "high"), and a
  document with >30% low-confidence cells is flagged for manual review.

## 2. Can you roll back after the DROP? **Yes.**

This is the question that decides whether the deploy is reversible, so here is
the mechanism rather than an assurance.

`2584bb6` — the commit you would roll back to — contains, in its own
`_run_migrations()`:

```sql
ALTER TABLE column_templates ADD COLUMN IF NOT EXISTS cell_binding_map TEXT;
```

That statement runs **inside the FastAPI lifespan, before the app serves any
traffic**, and before the FIX-7 block that queries the column. So the rollback
sequence is:

1. Redeploy `2584bb6`.
2. Container boots → `init_db()` → `_run_migrations()` → the column is
   re-created as `NULL` for all 19 rows.
3. FIX-7 then queries it, finds nothing, and moves on.
4. The app serves.

**What you lose on rollback:** the one stored CBM blob on template id 24. The
old code treats a `NULL` `cell_binding_map` as "legacy template" and falls back
to `compute_binding_map`, so extraction works; and the blob regenerates the next
time that template is saved. Nothing else is lost — no job, no document result,
no template grid.

`shape_json` needs no consideration: it does not exist in production.

**So the schema change is NOT one-way.** The only irreversible thing in this
deploy is time.

One caveat worth stating plainly: if you roll back and the ADD COLUMN itself
fails (it is inside the same `try/except`), the old code would raise on any
query touching `column_templates`. That failure mode is visible immediately —
`GET /api/templates` returns 500 — and is fixed by running the ADD COLUMN by
hand. It has never been observed; the statement is idempotent and the table is
tiny.

## 3. Deploy order: **backend first, then frontend.** This is not optional.

| order | outcome |
|---|---|
| **Backend, then frontend** | Safe. During the window, the old frontend still writes `extractTargets`; the new backend ignores them and derives slots from emptiness, reaching the same result. The only visible oddity is that the old editor still shows an "Extract here" button that no longer affects anything. |
| Frontend, then backend | **Breaks extraction.** The new editor saves grids with **no** `extractTarget` flags. The live backend's `_analyse_template_regions` builds `explicit_targets` from exactly that flag, and `has_explicit_targets` drives `primary_mode`. A grid with zero flags routes to the wrong mode. Any template saved during that window extracts wrongly. |

Verified rather than assumed: the live backend has 40 references to
`extractTarget`, including `explicit_targets` construction at lines 443/463 of
`extract.py`.

Because both services build from `main`, merging the branch will make **both**
eligible. Deploy the backend first and confirm it healthy before triggering the
frontend.

## 5. What a client still hits immediately

Each verified present in the code being deployed.

### Would be noticed on day one

| # | issue | effect |
|---|---|---|
| 1 | **Image uploads have no OCR.** `_extract_image_with_template` sends the image straight to Gemini Vision with no text layer, forces every confidence to `medium` and always sets `needs_review`. Grounding cannot run — there is no text to verify a span against. | A photographed or scanned-as-image document extracts unverified. It is the one path that never joined the single pipeline. |
| 2 | **A "Drive" tab leads nowhere.** The extract page renders it; `GoogleDriveConnector.authenticate()` uses `flow.run_local_server()`, a desktop OAuth flow that cannot complete in a container. | A client clicking it in a demo reaches dead functionality. Fails cleanly (400/401), but it is visible. |
| 3 | **Cancel does not cancel.** `DELETE /api/jobs/{id}` sets `status="cancelled"`; there is no cancellation check in the extraction loop and the thread unconditionally sets `completed` at the end. | Cancelling a long batch relabels it briefly; the work and the LLM spend continue. |
| 4 | **Jobs can be stranded `processing` forever.** Extraction runs in a `daemon=True` thread; there is no startup scan for orphans (`main.py` contains no such recovery). Any restart mid-batch — including this deploy — leaves those jobs polling at 2s intervals indefinitely. | See the pre-deploy check in §6. |

### Real but less immediately visible

| # | issue |
|---|---|
| 5 | **`_dump_raw_extraction` still writes customer data to disk on every successful extraction**, to a single fixed filename, from code commented "TEMPORARY DEBUG". Concurrent extractions overwrite each other. |
| 6 | **CORS is hardcoded `allow_origins=["*"]`.** The `CORS_ORIGINS` variable set on the service maps to no Settings field and is ignored. Mitigated by Bearer-token (not cookie) auth. |
| 7 | **`MAX_FILE_SIZE_MB` set in Railway is not read** — the code reads `MAX_UPLOAD_SIZE_MB`. Both happen to be 50, so there is no symptom; changing the Railway value does nothing. |
| 8 | **Template access is not ownership-checked on upload.** `POST /api/extract/upload` loads a `ColumnTemplate` by id with no `client_id` or owner check, unlike `get_template`. |
| 9 | **`PRIMARY_LLM` still defaults to `"groq"`** in code, and the Groq models configured are decommissioned. Production overrides it to `gemini`, so it works — but the default is a non-functional configuration for anyone running the repo. |
| 10 | Passwords are single-round salted SHA-256; a password change does not invalidate issued JWTs (only deactivating the user does). |

None of 1–10 is introduced by this deploy. All are pre-existing.

## 7. Rollback

**Trigger it if:** the backend boot log shows a traceback; `/health` does not
return 200; `GET /api/templates` 500s; or step 4 produces a sheet with no table
rows.

1. **Redeploy `92b54699`** (commit `2584bb6`) on `docagent-univer` from the
   Railway deployments list.
2. **Verify:** boot log shows `Database migrations applied`, then
   `curl /health` → 200, then
   ```sql
   SELECT column_name FROM information_schema.columns
   WHERE table_name='column_templates' AND column_name='cell_binding_map';
   ```
   → one row. The old code re-created it during boot. If it is missing, run
   `ALTER TABLE column_templates ADD COLUMN IF NOT EXISTS cell_binding_map TEXT;`
   by hand and restart.
3. **If the frontend was already deployed, roll it back too** — a new frontend
   against an old backend is the unsafe combination (§3).
4. Only if the database is somehow inconsistent, restore `B2`:
   `pg_restore -d "$DATABASE_URL" --clean --if-exists docagent-preDeploy-20260819.dump`.
   This should not be necessary; no data is written or migrated by this deploy.

**Templates saved through the new editor between deploy and rollback** will have
lost their `extractTarget` flags. Under the old code those templates route by
`explicit_targets` and will extract incorrectly until re-marked. This is the one
thing a rollback does not undo — which is the reason step 8 is placed last and
scoped to a template you can afford to re-save.
